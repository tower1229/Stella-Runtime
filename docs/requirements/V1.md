# Stella Runtime V1 requirements

> Status: historical 0.1 baseline
> Version: 1.0
> Last updated: 2026-08-11

This document preserves the repository-local requirement baseline used for the
published `0.1.0` line. It
contains the generic requirements extracted from the original architecture
interview. It deliberately excludes any private Agent's identity, knowledge,
configuration, paths, conversations, credentials, and lived-experience records.
It is not the current protocol authority: the current public Contract Set uses
the coherent `cognitive-runtime.<contract>/v2` namespace defined by
[`../architecture/DATA-CONTRACTS.md`](../architecture/DATA-CONTRACTS.md),
[`../../CONTEXT.md`](../../CONTEXT.md), and the accepted ADRs.

## 1. Product objective

Stella Runtime is an instance-neutral cognitive runtime for OpenClaw. It helps a
Private Instance use explicit, versioned, traceable, and correctable personal
knowledge without converting model inference or generated projections into a
hidden authority source.

The Runtime is not a second Agent loop, general memory system, vector database,
persona engine, value judge, or autonomous action authority. OpenClaw continues
to own sessions, the Agent loop, native memory tools, and native audit trajectory.

V1 must prove that the Runtime can:

1. bind one immutable authority generation and one State View to each Run;
2. keep current user input above stale state, long-term patterns, and history;
3. provide one bounded cognitive routing decision and a progressive context
   packet to the host Agent loop;
4. trace which governed knowledge roles affected a response without copying the
   full prompt, answer, or tool output;
5. commit an explicit correction transaction and safely deliver one successful
   successor response in a distinct Run;
6. export, verify, and restore its Authoritative Runtime State across hosts.

## 2. Authority principles

### DS-01 — Distinct authority layers

The data model separates:

- **Evidence**: source material and observations;
- **Semantic**: durable claims about reality;
- **Cognitive**: user-confirmed reasoning frameworks and governing direction;
- **Current State**: append-only changes to what is currently effective;
- **Episodic**: host-owned session events and summaries.

Evidence is not a claim. A Personal Model is a conditional, falsifiable Semantic
interpretation, not identity essence. A framework name, author text, model prior,
or inferred label never becomes a user's Cognitive definition without explicit
admission.

### DS-02 — Explicit authority over projections

An Authority Repository owns durable knowledge and configuration. Registry,
generation, digest, index, cache, and embedding are checksummed projections. They
must be disposable and rebuildable from one authority revision.

### DS-03 — Target-state-first invariants

The normal path automatically maintains one authority, one active generation,
and one State View per Run. Failure recovery restores the same target state; it
must not create a long-lived fallback architecture or second authority source.

### DS-04 — Compatible contract evolution

Existing stable IDs and authority semantics are preserved unless a versioned
migration demonstrates a concrete benefit. Breaking schema changes require an
explicit contract version, deterministic migration, rejection behavior, and
positive and negative fixtures.

## 3. Cognitive behavior requirements

### RT-01 — Single bounded Router

Each eligible Run performs at most one Router completion. Input is limited to the
current message, small recent context, the fixed State View, the active governing
binding, a compact registry, and generation metadata. The Router selects an
instance-declared retrieval plan and at most one primary plus one supporting
ordinary framework. It does not call tools, iterate, or answer the user.

The host owns model completion. Runtime parses a single JSON object, validates a
closed schema, then validates IDs, roles, versions, generation, and checksums
against the fixed registry. It never accepts a model-selected governing binding.

### RT-02 — Explicit degradation

Router timeout, empty output, non-JSON output, schema failure, unknown IDs, or
authority mutation produce a machine-readable degraded result. Runtime does not
retry the Router or silently reinterpret malformed output.

If retrieval is `required` and no valid memory reference is observed, Runtime may
request at most one bounded same-Run remediation. It must not switch the Run's
generation or State View.

### RT-03 — Progressive explicit context packet

The packet is minimal and role-aware. It distinguishes current input, State View,
Semantic claims, Evidence references, governing context, ordinary frameworks,
and retrieval instructions. `none` disables optional long-term retrieval and
ordinary framework expansion; it never disables a configured governing kernel.

### RT-04 — Native audit plus cognitive overlay

OpenClaw owns general execution evidence. Runtime stores only a Cognitive
Provenance Overlay keyed by `run_id`: selected IDs, roles, versions, generation,
State View, valid stable references, status, and failure reasons. It excludes the
full prompt, answer, tool payloads, and personal document bodies.

### RT-05 — Immutable State View and correction

Each Run pins one immutable State View. Current State uses an append-only event
ledger plus an active head. A correction atomically appends its event, advances
the head, and creates a re-answer outbox record. An old Run never adopts the new
View; a distinct successor Run does.

Delivery is at-least-once across attempts and exactly once for successful
completion. Failed or aborted attempts return to pending. Duplicate correction
IDs are idempotent. Runtime must never claim cross-Run exactly-once delivery.

### RT-06 — Minimal verified host integration

V1 uses the verified typed hooks `before_prompt_build`, `after_tool_call`,
`before_agent_finalize`, and `agent_end`. A bounded `RunScratchMap` is keyed only
by `run_id`, pins immutable references, records tool observations idempotently by
`toolCallId`, and is cleared through `agent_end`, lifecycle cleanup, TTL, and a
hard capacity limit. Missing `run_id` degrades; `sessionKey` is not a fallback.

### RT-07 — Atomic generation visibility

Builder validates one authority revision, stages all derived artifacts, and
atomically activates one `sync_generation`. Registry, governing digest, knowledge
projection, and index metadata visible to a new Run must share that generation.
Mixed generations block activation.

### RT-08 — Governing context is instance-declared

The public protocol permits zero or one active Governing System. If configured,
its Kernel is bound to each eligible private main Run and cannot be disabled by
ordinary framework routing. Modules remain on demand. No concrete philosophy,
belief, or worldview is built into the Runtime.

### RT-09 — Framework admission

`framework-admission` separates source-author claims, model synthesis, and the
user's accepted, rejected, or rewritten understanding. Only explicitly confirmed
content enters Cognitive authority. Each admitted entity states direction,
attention, strengths, compression risks, blind spots, applicable boundaries,
counterexamples, relations, sources, and runtime digest.

### RT-10 — Authoritative Runtime recovery

`RuntimeRecoveryPort` provides `backup`, read-only `verify`, and rollback-safe
`restore`. The versioned, checksummed, credential-free snapshot contains the
Current State Event Ledger, active head and view boundary, unfinished correction
and ReanswerOutbox state, storage schema, package and contract versions, instance
ID, authority revision, and file integrity data.

Live SQLite copying is forbidden. Storage migration belongs inside Runtime.
Rebuildable generation, Registry, Index, and cache are excluded. Traces, logs,
raw experience records, credentials, and private authority documents are excluded
unless a future versioned contract explicitly changes their classification.

## 4. Distribution and compatibility requirements

### PUB-01 — Single package

The project publishes one scoped package:
`@tower1229/stella-cognitive-runtime`. It contains Plugin runtime, CLI, public
contracts, generated runtime types, the `framework-admission` Skill, self-check,
and required runtime assets. It does not create independent CLI or Skill release
lines.

### PUB-02 — Public identity

- project: Stella Runtime;
- repository: `tower1229/Stella-Runtime`;
- Plugin ID: `cognitive-runtime`;
- historical 0.1 schema namespace: `cognitive-runtime.<contract>/v1`;
- Node.js: `^22.19.0 || ^24.0.0`;
- license: MIT.

The Stella brand is not a public protocol namespace.

### PUB-03 — Exact-host compatibility

Support is declared by release channel plus exact OpenClaw version and a committed
capability result. A minimum-version comparison never enables behavior. Each new
host row must pass package install, runtime inspect, typed-hook correlation,
model-completion validation, memory-reference extraction, successor delivery,
cleanup, and failure-path smoke.

### PUB-04 — Privacy and package content

Repository, CI, examples, Golden fixtures, logs, and npm tarball use synthetic
data only. They contain no private identity, knowledge, conversations, runtime
database, credentials, machine paths, real experience, or private Instance Test
Pack. Tarball contents are allowlisted and scanned before release.

### PUB-05 — External consumer seam

The public Runner may accept an external Instance Test Pack path. This is an
optional input to consumer verification, not an implementation dependency. All
Runtime requirements and release gates remain executable with repository-owned
synthetic fixtures.

### PUB-06 — Reversible release

V1 supports `off`, `observe`, and `enforce` deployment states. `observe` executes
and reports Runtime decisions but does not inject private cognitive context.
Package rollback installs the previous verified exact version. Data recovery uses
the Recovery Snapshot contract. A successful V1 removes the legacy implementation
instead of maintaining a permanent parallel architecture.

## 5. Quality gates

V1 technical release requires:

- generated types and runtime validation agree with every public schema;
- duplicate IDs, broken references, wrong authority roles, mixed generations,
  missing cognitive boundaries, and invalid state transitions fail deterministically;
- concurrent hooks, repeated hooks, TTL, capacity, lifecycle cleanup, correction
  rollback, outbox retry, and single-success completion pass;
- package build, test, typecheck, lint, `npm pack`, tarball allowlist, sensitive
  scan, install, inspect, CLI discovery, Skill discovery, and self-check pass;
- exact-host smoke proves all claimed capabilities and all explicitly unsupported
  paths fail closed;
- recovery succeeds or safely rejects normal, checksum-damaged, incompatible,
  pending-outbox, interrupted, instance-mismatch, and repeated-restore fixtures;
- non-LLM Plugin processing starts with a p95 target of 100 ms or less, excluding
  host model completion and host memory tools;
- every failure branch emits a bounded machine-readable reason without private
  content.

Consumer product acceptance is deliberately outside the Runtime release gate. A
Private Instance may run real-life comparisons and usefulness judgment, but those
records never become public Runtime fixtures.

## 6. Explicit exclusions

V1 does not include a second Agent loop, general-purpose vector store, hidden
personal model, automatic framework promotion, arbitrary action authorization,
RBAC, governance dashboard, generic migration product, complete erasure workflow,
automatic retention policy, cloud disaster recovery, or bare-metal imaging.
